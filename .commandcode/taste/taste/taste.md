# Taste
- Gives terse, imperative go-ahead directives ("Go ahead and enable automatic updates") rather than detailed specs, and expects the work to be carried through to a verified result without back-and-forth confirmation. Confidence: 0.7
- Cites the authoritative upstream documentation URL when requesting a feature, treating it as the spec — the implementation is expected to follow that official recipe rather than a hand-rolled equivalent. Confidence: 0.7
- Interrogates unexplained slowness or cost in a run ("why too long? is it because host internet speed is slow?") instead of waiting it out, and offers a plausible hypothesis — expects the root cause to be found and quantified, including the possibility that the agent's own recent change is to blame rather than the environment. Confidence: 0.6
- Debugs by pasting verbatim terminal captures from the live machine or build logs (shell prompt or timestamped log tail included, e.g. `root@templates:~# cat /etc/network/interfaces`) with no accompanying question, and expects the agent to read the raw output, spot the anomaly itself and diagnose from evidence rather than being told what to look at. For deployed-instance issues judgement is based on the live runtime state, not on build artifacts or the agent's report. Confidence: 0.7
- When filing a bug, states the observed symptom plus their own root-cause hypothesis and the exact files involved ("Solve the problem of applying for a DHCP IP twice due to duplicate config at … => 1 interface is granted up to 2 IPs") — expects the fix applied permanently at the source of truth (the image build / repo config), not a hand edit on the affected running host. Confidence: 0.6
- Expects a claimed fix to be proven against the real production condition, not the convenient local one — a reproduction that happens to hide the bug (e.g. an empty datasource seed) counts as unverified. Confidence: 0.5
- Draws a hard line between kicking off a long-running build and watching it: "Just run the build tool and stop there; there is no need to monitor the process—I will let you know if any errors arise." For builds/CI-style jobs, launch the documented command once, report that it started, and do not tail logs, poll for completion, or babysit — the user acts as the error reporter. (This scopes the general "carry work to a verified result" expectation: verification of *correctness* is wanted, but synchronous monitoring of *progress* is not.) Confidence: 0.8
- Asks for new variants by extending a named, currently-working artifact ("The currently built Debian 12 template is working well. Building on this success, create Debian 13 and Debian 11") — expects the proven config to be used as the template/reference to fork from, rather than a from-scratch redesign or a question about which approach to take; likewise expects a fix/change to be rolled out consistently across all maintained versions (e.g. UEFI switch for 11 "like in Debian 12—please include the configuration for Debian 13 as well"). Confidence: 0.7
- Prefers UEFI boot (GPT + ESP, Secure Boot-capable) over legacy MBR/BIOS for all Debian images, using the Debian 12 UEFI setup as the reference standard. Confidence: 0.8
